# 서버 백업·복구 설계서

> 🔴 **목표 한 줄: 폰을 잃어도 단어·카테고리·퀴즈 기록·AI 성적표가 돌아온다.**
>
> 2026-10-12 사장님 지시. *"카테고리, 단어, 퀴즈 결과(ai 포함), 잔디(출석) 등등 모든 데이터를
> 저장하고 싶은데"* — 어느 저장소냐를 여쭈었고 **「서버에도 전부 (폰 잃어도 복구)」** 를 고르셨다.

## 1. 목표와 비목표

| | |
|---|---|
| ✅ 목표 | 새 기기에서 **내 학습 전체**를 되살린다 |
| ✅ 목표 | 지금 쓰는 사람에게 **보이는 변화 0** — 로그인은 선택이다 |
| 🚫 비목표 | 여러 기기 **동시 사용**(실시간 양방향 병합). 복구는 한 방향 사건이다 |
| 🚫 비목표 | 백업 파일 폐기. 파일은 로그인 없이 쓰는 사람의 유일한 수단으로 **남긴다** |

### ⚠ 잔디(출석)는 이 설계서에서 **표를 만들지 않는다**

`quizService.calculateStreak()` 가 `quiz_results.taken_at` 을 세어 그때그때 만든다. 홈의
`🔥 N일 연속`·7일 막대·오늘 카드가 전부 그렇다. **원천을 복구하면 잔디는 저절로 따라온다.**

🔴 따로 저장하면 두 곳이 어긋난다 — 기록은 돌아왔는데 잔디는 안 돌아오거나, 그 반대가 된다.
이 저장소가 `@my_word_srs`(복습 만기)를 백업에서 **일부러 뺀** 것과 같은 판단이다.

### 서버 — **단어만 간다. 그것도 밀기만**

| | 서버에 있나 |
|---|---|
| 단어 | ✅ `user_words` |
| 카테고리 | ❌ |

🟢 **그 장벽은 로그인이 치운다. 그리고 로그인은 공통 서버에 이미 있다**(§6).

## 3. 🔴 읽고 나서 계획이 바뀐 것 둘

### ① 묘비는 생각보다 **싸다** — 읽는 쪽은 이미 다 걸러 놓았다

`repo.ts` 를 열어 보니 **읽기 전부가 이미 `deleted_at IS NULL` 을 걸고 있다.**

```
categoryRepo.getAll / getById        WHERE deleted_at IS NULL   ✅ 이미
wordRepo.getAll / getByCategoryId / getById   같음               ✅ 이미
```

바꿀 곳은 **지우는 두 함수뿐**이다(`wordRepo.delete` · `categoryRepo.delete`).
스키마의 `deleted_at` 칸도 **양쪽에 이미 있다.** 처음 생각한 「읽는 곳 전부 손대기」가 아니다.

### ② 탈퇴가 학습 데이터를 **안 지운다** — 이건 일을 늘린다

`lib/auth/subject.ts` 의 `softDeleteSubject` 는 진단 요약만 지우고 주체를 가명화한다.
**`user_words` 는 건드리지 않는다.** `subjectId` 에 `onDelete: cascade` 가 걸려 있지만
소프트삭제는 그 연쇄를 일으키지 않는다.

🔴 지금은 단어만이라 작지만, **학습 전체를 올리기 시작하면 이건 파기 의무가 걸린 데이터다.**
그래서 §4 의 표를 만들 때 **지우는 쪽도 같이** 만든다.

### ③ 🔴 게시된 처리방침이 **퀴즈 기록과 시험을 부정하고 있다** — 이것이 가장 크다

표와 라우트를 다 만든 뒤에 `docs/privacy-policy.html` 본문을 읽고 알았다. **지금 게시 중인**
문서(2026-10-07 개정)가 이렇게 말한다:

```
「그 밖의 항목(메모·예문·태그·퀴즈 기록·설정)은 기기 밖으로 나가지 않습니다」
「시험의 점수와 답안은 기기에만 저장되며 서버로 전송되지 않습니다」
```

🔴 **로그인과 무관하게, 코드를 켜는 것만으로 게시된 약속을 어긴다.** 처음에는 B(법무)가
C(로그인) 앞이면 된다고 적었는데, 실제로는 **A 에서 미는 것부터** 걸린다.

그래서 A 는 **셋을 꺼 둔 채로** 끝낸다:

```
ENABLED_KINDS = ['words']      ← 단어는 제5-3항으로 이미 공시됐다
```

🔴 **기계가 지킨다** — `__tests__/syncDisclosure.test.ts` 가 `ENABLED_KINDS` 와 처리방침
본문을 대조해 공시되지 않은 종류가 켜져 있으면 FAIL 한다. 그 가드 자신이 0개를 검사하고
초록이 되지 않도록 *"지금 처리방침은 퀴즈 기록·시험을 부정하고 있다"* 를 함께 확인한다
(문구가 사라지면 가드가 먼저 빨개진다).

⚠ **카테고리도 꺼 둔다.** 제5-3항은 「단어와 그 뜻」만 적고 단어장 **이름**은 적지 않았다.
`user_words.category_id`(숫자)는 이미 가고 있지만 이름은 다른 항목이다.

## 4. 🔴 묘비 — 왜 이것이 1번인가

지금 단어 삭제는 하드 삭제다. *"지웠다"* 는 사실이 남지 않아 서버에 갈 것이 없다.

```
지금     지움 → 기기에서 사라짐 · 서버엔 남음        밀기만 하니 아무도 안 다친다
당기기 후  지움 → 기기에서 사라짐 → 🔴 복구하면 되살아난다
```

**당기기를 켜는 순간 이것이 버그가 된다.** 그래서 묘비가 먼저다.

- `wordRepo.delete` → `UPDATE words SET deleted_at = ?, updated_at = ?`
- `categoryRepo.delete` → 같은 트랜잭션에서 카테고리와 그 안의 단어를 함께 묘비로
- `updated_at` 을 **같이 올린다** — 밀기가 `lastUpdatedAt` 이후만 보내므로, 안 올리면 묘비가 **영원히 안 밀린다**
- ⚠ `backupRepo.restore` 의 `DELETE` 는 **그대로 둔다.** 거기는 전부 지우고 다시 넣는 자리라 하드 삭제가 맞다
- ⚠ 복원은 묘비도 지운다 → 복원 뒤 서버에 삭제 사실이 전달되지 않는다. §7 의 되감기가 덮는다

### 기계로 막을 것

소스 검사로 **`DELETE FROM words|categories` 가 `backupRepo` 밖에 있으면 FAIL**.
오늘 잡은 「읽기는 SQLite, 쓰기는 AsyncStorage」와 같은 종류의 어긋남이 생길 자리다.

## 5. 서버 표 셋

`user_words` 의 모양을 그대로 따른다 — `(app_code, subject_id, <기기 id>)` 복합키 ·
기기 시각을 **서버 시각으로 덮지 않는다** · `synced_at` 은 따로.

```
user_categories    subject_id + category_id        이름 · 설명 · 순서 · 생성/수정/묘비
user_quiz_results  subject_id + result_id          word_id · 정답여부 · 유형 · 푼 시각
user_exams         subject_id + exam_id(TEXT)      언어 · 카테고리 · 문제(JSON) · 회차(JSON) · 점수(JSON)
```

### ⚠ 퀴즈 결과는 **끝없이 늘어난다. 그래도 자르지 않는다**

한 문제가 한 줄이다. 하루 10문제면 1년에 3,650줄, 사람이 늘면 곱해진다.

🔴 **그래도 상한을 두지 않는다.** 복구의 오라클이 **「복구 뒤 통계 == 복구 전 통계」** 이고,
결과를 자르면 그 오라클이 깨진다 — 복구했더니 정답률이 다른 것은 **복구가 아니다.**
1.5.0·1.6.0·1.8.0 의 백업 검증이 셋 다 이 한 줄을 오라클로 썼다.

→ 대신 **주체당 행 수를 관리자 화면에 띄우고**, 1만 건을 넘는 주체가 나오면 그때 접는 규칙을 정한다.
지금 사장님 폰이 수십 건이다. 없는 문제를 미리 풀지 않는다.

### 탈퇴할 때 지운다

`softDeleteSubject` 에 세 표 + `user_words` 삭제를 **같이** 넣는다(§3②).

## 6. 신원 — 서버에 이미 다 있다

```
POST /v1/auth/login    구글 ID 토큰 → 세션          배포·검증 완료
GET  /v1/auth/me
subjects               provider: google | kakao | apple | device
                       탈퇴 시 provider_id 가명화 → 재로그인으로 부활 안 함
app_auth_providers     앱별 클라이언트 ID (재배포 없이 켠다)
```

앱이 `provider: 'device'` 로만 등록하고 있을 뿐이다. 형제 앱이 이 로그인을 이미 쓴다.

### 🔴 승계 — 병합을 만들지 않는다

구글로 로그인하면 **새 주체**가 생기고 기기 주체의 사본은 고아가 된다. 병합 코드를 쓰지 않는다:

> **기기가 정본이다.** 로그인한 뒤 전부 **다시 민다.** 고아가 된 기기 주체의 행은 관리자가 치운다.

병합은 두 계정의 데이터를 섞는 코드이고, 틀리면 **남의 단어가 내 단어장에 들어온다.**
그 위험을 「다시 밀기」 한 번으로 피할 수 있으면 피한다. `syncService` 에 되감기(`needsRewind`)가
**이미 있다** — 주체가 바뀌면 `serverTotal` 이 0 으로 보이므로 되감기가 저절로 걸린다.
⚠ 그래도 **주체 변경 시 상태 초기화를 명시적으로** 넣는다. 저절로 되는 것에 기대지 않는다.

## 7. 당기기 — 라우트와 충돌 규칙

```
GET /v1/sync/counts                              { words, categories, results, exams }
GET /v1/sync/pull?kind=categories
GET /v1/sync/pull?kind=words&after=<id>&limit=500
GET /v1/sync/pull?kind=results&after=<id>&limit=1000
GET /v1/sync/pull?kind=exams&after=<takenAt>&limit=50
POST /v1/sync/push   { kind, items[] }           ← 네 종류를 한 라우트로
```

⚠ `counts` 가 따로 있는 이유: 복구 화면이 **아무것도 내려받기 전에** 「가져올 게 있나」를
말해야 한다. 싸고, 그 화면의 「서버」 칸이 그대로 이 값이다.
⚠ `POST /v1/words/sync` 는 **그대로 둔다** — 그걸 부르는 번들이 이미 기기에 깔려 있다.

### 충돌은 코드가 정하지 않는다. 사람이 고른다

```
기기가 비어 있다(단어 0)  → 묻지 않고 가져온다
기기에 뭐가 있다          → 🔴 양쪽 숫자를 나란히 놓고 고르게 한다
```

백업 복원 시트가 **이미 그 모양**이다(`지금 기기 단어 2 · 퀴즈 3` vs `백업 단어 8 · 퀴즈 12`).
사장님이 이미 보신 화면이라 새로 배울 것이 없고, 1.5.0·1.6.0·1.8.0 에서 세 번 검증된 통로다.

🔴 **가져오기는 「합치기」가 아니라 「덮어쓰기」다.** 합치면 같은 id 가 서로 다른 단어를 가리키는
경우를 다뤄야 하고, 그 코드는 틀렸을 때 **조용히 틀린다.** 덮어쓰기 직전에 지금 기기 상태를
`myword-before-restore.json` 으로 남긴다 — **복원이 이미 하는 일을 그대로 쓴다.**

### 🟢 서버 계약은 끝까지 쟀다 — `common_server/tools/_dv_sync.ts` · **37건 ALL PASS**

```bash
BASE_URL=https://common-server.vercel.app APP=myword \
  node --env-file=.env.local tools/_dv_sync.ts
```

백로그에 *"셋을 켜는 날 먼저 만든다"* 로 적어 둔 그 도구다. **운영 배포본**을 상대로
자기 시험 주체를 만들어 쓰고 탈퇴로 치운다. 눈으로 못 보는 셋이 전부 실측됐다:

| | 결과 |
|---|---|
| 묘비가 pull 에 안 나오나 | ✅ 네 종류 전부 |
| 순서역전(과거 `updatedAt` 이 최신을 덮나) | ✅ 안 덮는다 · 전진은 덮는다 |
| 결과 멱등(같은 `resultId` 를 다른 내용으로) | ✅ 안 바뀐다 |
| 회차 역전(짧은 `attempts` 가 긴 것을) | ✅ 못 덮는다 · 늘어난 것은 덮는다 |
| 상한 · 커서 전진 · `after` 쓰레기 | ✅ 400 / 끝에서 `null` / 처음부터 |
| 🔴 탈퇴 뒤 네 표가 0행 | ✅ (지우기 **전** 행 수를 먼저 세서 0을 성공으로 안 읽는다) |

🔴 **변이로 5건 확인했다.** 깨뜨리면 가드가 정확히 그 줄을 짚는다 — 특히 탈퇴의
`delete(userWords)` 를 지우면 `{"user_words":4,…}` 가 나온다. **10-12 까지 실제로 그 상태였다.**

### 🟢 고쳤다 — **넣는 순간 간다** (2026-10-13 사장님 지시 · `src/services/syncScheduler.ts`)

> *"그냥 단어 저장, 수정, 삭제 할 때마다 서버로 보내면 안돼? … 인터넷 안되는 환경에서
> 하면 안되다가 인터넷 연결되면 그 때 보내게 처리해도 좋잖아"*

🔴 **내가 처음에 반대한 근거가 틀렸다.** 나는 *"10개를 연달아 넣으면 요청이 10번 나간다"* 로
반대했는데, 그건 **「저장할 때마다 민다」와 「저장 한 건에 요청 한 번」을 같은 말로 본 것**이다.
둘은 같은 말이 아니다 — 마지막 입력에서 **3초를 묶으면(디바운스)** 10개는 요청 **한 번**이 된다.
반대의 근거가 사라졌으므로 반대도 사라진다.

```
저장·수정·삭제   → 3초 묶음 뒤 한 번      (syncScheduler.schedule)
앱으로 복귀       → 묶지 않고 바로         (syncScheduler.now)
한 배치에 남음    → 1초 뒤 이어서          (MORE_MS)
실패              → 30초 → 2분 → 5분 반복  (BACKOFF_MS)
서버 설정 없음    → 영원히 같으니 멈춘다    ('off')
```

🔴 **「인터넷이 돌아오면 그때」를 네트워크 모듈 없이 한다.** 상태를 듣는 모듈을 넣으면
`runtimeVersion` 이 올라가 **지금까지 낸 OTA 가 전부 끊긴다.** 백그라운드 백업에서
「붙는 그 순간」과 「붙고 30초 안」의 차이는 사용자에게 의미가 없다.

🟢 **큐를 안 만들었다. 이미 있다** — `pickChanged` 가 `updated_at > 마지막으로 민 시각`을
고르고, 실패하면 그 시각이 안 움직인다. **기기 DB 자체가 큐다.**

## 9. 재는 법

🔴 **오라클은 하나다 — 복구 직후 통계 == 복구 전 통계.** 백업 검증이 세 릴리스에서 쓴 그 줄이다.

| 무엇 | 어떻게 |
|---|---|
| 묘비가 밀리나 | 단어를 지우고 밀기 → 서버 행의 `deleted_at` 이 찍힌다 |
| 🔴 지운 단어가 안 살아나나 | 지우고 → 밀고 → 기기 비우고 → 당기기. **그 단어가 없어야 한다** |
| 복구 뒤 통계 | 단어·카테고리·정답률·🔥연속·오늘 N문제가 **전부 복구 전과 같다** |
| 🔴 잔디 | 7일 막대의 날짜별 높이가 복구 전과 같다 — 파생이 제대로 재생됐다는 증거 |
| AI 성적표 | 회차·점수·오답노트가 돌아온다(`attempts` 구조 보전) |
| 탈퇴 | 탈퇴 뒤 네 표에 그 주체의 행이 **0건** |
| 상한 | 500개를 한 번에 밀면 나뉘어 간다 · 서버 `MAX_BATCH` 를 넘기면 거절한다 |

⚠ **화면만 보고 통과시키지 않는다.** 1.6.0 의 SRS 버그가 화면으로는 정상이었고
`sqlite3` 로 저장본을 뜯은 것이 유일한 오라클이었다. 서버 쪽은 행을 직접 센다.
